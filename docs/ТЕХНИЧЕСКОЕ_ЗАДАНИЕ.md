# Техническое задание

## Веб-сервис для автоматизированного построения и визуализации бизнес-процессов компаний

---

**Версия:** 1.0  
**Дата:** 05 февраля 2026 г.  
**Статус:** Утверждено

---

## 1. Общие сведения

### 1.1. Наименование системы

**Полное наименование:** Веб-сервис для автоматизированного построения и визуализации бизнес-процессов компаний с использованием искусственного интеллекта

**Краткое наименование:** Business Process Builder (BPB)

### 1.2. Назначение системы

Система предназначена для автоматизированного создания, визуализации и оптимизации бизнес-процессов организаций на основе структурированного интервью с использованием технологий искусственного интеллекта. Сервис позволяет преобразовать описание деятельности компании в формализованные бизнес-процессы с визуализацией в формате BPMN 2.0 Swimlane.

### 1.3. Цели создания системы

| № | Цель | Ожидаемый результат |
|---|------|---------------------|
| 1 | Сокращение времени на описание бизнес-процессов | Снижение трудозатрат с 40-80 часов до 15-30 минут |
| 2 | Стандартизация описания процессов | Единый формат BPMN 2.0 для всех процессов |
| 3 | Автоматизация анализа процессов | Генерация рекомендаций по оптимизации |
| 4 | Интеграция с внешними системами | Экспорт в Camunda, Bizagi и другие BPMN-платформы |

### 1.4. Целевая аудитория

Система ориентирована на следующие категории пользователей:

**Бизнес-аналитики и консультанты** — специалисты, занимающиеся описанием и оптимизацией бизнес-процессов клиентов. Для них система предоставляет инструмент быстрого создания формализованных описаний процессов.

**Руководители подразделений и владельцы процессов** — менеджеры среднего и высшего звена, которым необходимо документировать и стандартизировать процессы своих подразделений без привлечения внешних консультантов.

**Собственники малого и среднего бизнеса** — предприниматели, стремящиеся систематизировать операционную деятельность компании для масштабирования или передачи управления наёмным менеджерам.

## 2. Функциональные требования

### 2.1. Модуль сбора информации

#### 2.1.1. Структурированное анкетирование

Система должна предоставлять интерактивную форму анкетирования, состоящую из тематических блоков вопросов:

| Блок | Название | Количество вопросов | Описание |
|------|----------|---------------------|----------|
| A | Общая информация о компании | 5 | Сфера деятельности, структура, ключевые продукты |
| B | Описание процесса | 8 | Цель, участники, триггеры, результаты |
| C | Этапы и действия | 10 | Последовательность шагов, ответственные, сроки |
| D | Информационные системы | 6 | Используемые ИТ-системы, интеграции, документооборот |
| E | Метрики и KPI | 5 | Показатели эффективности, целевые значения |
| F | Проблемы и узкие места | 8 | Текущие сложности, потери времени, дублирование |
| G | Требования к оптимизации | 8 | Желаемые улучшения, приоритеты автоматизации |

**Общее количество вопросов:** 50 (полная версия) / 10 (сокращённая версия)

Система должна поддерживать два режима анкетирования:
- **Полный режим** — все 50 вопросов для детального описания процесса
- **Экспресс-режим** — 10 ключевых вопросов для быстрого создания базовой схемы

#### 2.1.2. Голосовое интервью

Система должна поддерживать голосовой ввод ответов на вопросы анкеты с последующей транскрипцией. Требования к голосовому модулю:

- Запись аудио в браузере без установки дополнительного ПО
- Автоматическая транскрипция речи в текст с использованием Whisper API
- Поддержка русского и английского языков
- Максимальная длительность одной записи — 5 минут
- Максимальный размер аудиофайла — 16 МБ
- Возможность редактирования транскрипции перед сохранением

#### 2.1.3. Сохранение черновиков

Система должна автоматически сохранять прогресс заполнения анкеты:

- Автосохранение каждые 30 секунд при наличии изменений
- Возможность возврата к незавершённому интервью
- Хранение черновиков в течение 30 дней
- Индикация процента заполнения анкеты

### 2.2. Модуль генерации бизнес-процессов

#### 2.2.1. Генерация структуры процесса

На основе ответов анкеты система должна автоматически генерировать структурированное описание бизнес-процесса, включающее:

**Общая информация о процессе:**
- Название процесса
- Цель и назначение
- Владелец процесса
- Границы процесса (начало и конец)

**Участники процесса (роли):**
- Перечень ролей с описанием зоны ответственности
- Организационная принадлежность
- Требуемые компетенции

**Этапы процесса:**
- Крупные стадии (уровень 0)
- Детальные шаги внутри каждого этапа
- Логическая последовательность выполнения

**Шаги процесса:**

| Атрибут | Описание |
|---------|----------|
| ID | Уникальный идентификатор шага |
| Название | Краткое наименование действия (глагол) |
| Описание | Детальное описание выполняемых действий |
| Тип | Start, Action, Product, Decision, Split, End |
| Роль | Ответственный исполнитель |
| Этап | Принадлежность к этапу процесса |
| Время выполнения | Нормативная длительность (минуты/часы/дни) |
| Входные данные | Документы и информация на входе |
| Выходные данные | Результаты и артефакты |
| Информационные системы | Используемые ИТ-инструменты |
| Связи | Предшествующие и последующие шаги |

**Ветвления и условия:**
- Точки принятия решений (XOR Gateway)
- Параллельные ветки (AND Gateway)
- Условия переходов между ветками

#### 2.2.2. Типы блоков процесса

Система должна поддерживать следующую библиотеку блоков для визуализации:

| Тип блока | Форма | Цвет обводки | Назначение |
|-----------|-------|--------------|------------|
| Start | Пилюля (скруглённый прямоугольник) | Зелёный (#22c55e) | Начало процесса |
| Action | Шестиугольник | Чёрный (#000000) | Действие/операция |
| Product | Скруглённый прямоугольник | Чёрный (#000000) | Результат/продукт |
| Decision | Ромб с символом "?" | Синий (#3b82f6) | Точка ветвления (XOR) |
| Split | Перевёрнутый треугольник | Синий (#3b82f6) | Параллельное разделение (AND) |
| End | Прямоугольник с двойными линиями | Красный (#ef4444) | Завершение процесса |

**Параметры блока Action:**

| Параметр | Иконка | Описание |
|----------|--------|----------|
| time | ⏱ | Время выполнения |
| document | 📄 | Входные/выходные документы |
| database | 🗄 | Информационные системы |
| stage | 📊 | Этап воронки/статус |

### 2.3. Модуль визуализации

#### 2.3.1. Диаграмма Swimlane

Система должна отображать бизнес-процесс в формате Swimlane (дорожки) со следующими характеристиками:

**Структура диаграммы:**
- Вертикальные дорожки для каждой роли (участника процесса)
- Горизонтальные секции для этапов процесса
- Блоки процесса размещаются на пересечении роли и этапа
- Связи между блоками отображаются ортогональными линиями

**Визуальные параметры:**
- Размер блока: 350×250 пикселей (настраиваемый)
- Толщина линий связей: 2 пикселя
- Цветовая палитра дорожек: 7 пастельных цветов
- Стрелки на концах связей для указания направления потока

**Интерактивность:**
- Масштабирование (zoom) от 0.5x до 2x
- Прокрутка (pan) для больших диаграмм
- Выделение блока при клике для просмотра деталей
- Подсветка связанных блоков при наведении

#### 2.3.2. Стандарт BPMN 2.0

Визуализация должна соответствовать стандарту BPMN 2.0:

**Sequence Flow (поток управления):**
- Сплошная линия со стрелкой
- Соединяет последовательные элементы процесса
- Подписи условий на ветках из XOR Gateway в квадратных скобках [условие]
- Маркер default ветки (косая черта) для ветки по умолчанию

**Правила маршрутизации стрелок:**
- Ортогональные коннекторы (только горизонтальные и вертикальные линии)
- Стрелки обходят блоки снаружи (сверху или снизу)
- Минимизация пересечений между стрелками
- Автоматический расчёт оптимального маршрута

#### 2.3.3. Экспорт диаграммы

Система должна поддерживать экспорт диаграммы в следующие форматы:

| Формат | Расширение | Назначение |
|--------|------------|------------|
| PNG | .png | Растровое изображение для презентаций и документов |
| BPMN XML | .bpmn | Стандартный формат для импорта в BPMN-системы |
| PDF | .pdf | Печатная версия с высоким разрешением |

**Требования к BPMN XML экспорту:**
- Соответствие спецификации BPMN 2.0
- Включение BPMNDiagram с координатами элементов
- Совместимость с Camunda, Bizagi, draw.io
- Корректный маппинг типов блоков на BPMN-элементы

### 2.4. Модуль редактирования процессов

#### 2.4.1. Интерактивное редактирование блоков

Система должна предоставлять возможность редактирования отдельных блоков процесса:

- Изменение названия и описания блока
- Изменение типа блока
- Редактирование параметров (время, документы, системы)
- Добавление и удаление связей с другими блоками
- Удаление блока из процесса

#### 2.4.2. AI-ассистент для изменений

Система должна поддерживать текстовые запросы на изменение процесса с обработкой через ИИ:

**Функция "Запросить изменения":**
- Текстовое описание желаемых изменений на естественном языке
- Автоматическая генерация обновлённой структуры процесса
- Предпросмотр изменений с визуальным diff (добавлено/удалено/изменено)
- Подтверждение или отклонение изменений пользователем

**Версионирование процессов:**
- Автоматическое сохранение версии перед применением изменений
- История всех версий процесса
- Возможность отката к любой предыдущей версии
- Отображение даты и описания каждой версии

#### 2.4.3. Регенерация процесса

Система должна позволять полностью перегенерировать процесс на основе исходной анкеты:

- Кнопка "Сгенерировать заново" с диалогом подтверждения
- Сохранение предыдущей версии перед регенерацией
- Индикатор прогресса во время генерации
- Уведомление о завершении генерации

### 2.5. Модуль рекомендаций

#### 2.5.1. Автоматический анализ процесса

Система должна анализировать сгенерированный процесс и формировать рекомендации по оптимизации:

| Категория | Описание | Примеры рекомендаций |
|-----------|----------|----------------------|
| Автоматизация через ИИ | Задачи, которые можно автоматизировать с помощью ИИ | Автоматическая классификация заявок, генерация ответов |
| CRM-интеграция | Оптимизация через CRM-системы | Автоматическое создание сделок, триггерные уведомления |
| Чат-боты | Внедрение диалоговых интерфейсов | Первичная квалификация лидов, FAQ-поддержка |
| Табличная автоматизация | Использование электронных таблиц | Автоматический расчёт показателей, сводные отчёты |
| 1С-интеграция | Автоматизация через 1С | Автоматическое формирование документов, синхронизация данных |

#### 2.5.2. Генерация воронок CRM

На основе процесса система должна генерировать варианты воронок для CRM-систем:

- 3 варианта воронки с разной детализацией
- Этапы воронки с привязкой к шагам процесса
- Рекомендуемые автоматизации для каждого этапа
- Метрики конверсии между этапами

#### 2.5.3. Расчёт метрик процесса

Система должна автоматически рассчитывать ключевые метрики:

| Метрика | Описание | Единица измерения |
|---------|----------|-------------------|
| Общее время процесса | Сумма времени всех шагов | Часы/дни |
| Критический путь | Максимальная длительность последовательности | Часы/дни |
| Затраты на ФОТ | Стоимость труда участников | Рубли |
| Количество передач | Число переходов между ролями | Штуки |
| Точки контроля | Количество точек принятия решений | Штуки |

### 2.6. Модуль управления компаниями

#### 2.6.1. Создание и редактирование компаний

Система должна позволять пользователям создавать профили компаний:

- Название компании
- Сфера деятельности
- Описание
- Контактная информация
- Логотип (опционально)

#### 2.6.2. Управление процессами компании

Для каждой компании система должна хранить:

- Список всех созданных бизнес-процессов
- Возможность просмотра, редактирования и удаления процессов
- Фильтрация и поиск по процессам
- Статус процесса (черновик, активный, архивный)

#### 2.6.3. Прикрепление документов

Система должна позволять прикреплять документы к компании:

- Загрузка файлов (PDF, DOCX, XLSX, изображения)
- Хранение в облачном хранилище (S3)
- Максимальный размер файла — 50 МБ
- Использование документов как контекста для генерации процессов

### 3.1. Требования к производительности

| Параметр | Требование |
|----------|------------|

| Время генерации процесса | < 60 секунд |

| Одновременных пользователей | > 100 |
| Доступность системы | 99.5% |

### 3.2. Требования к безопасности

**Аутентификация:**
- Регистрация по email и паролю
- Хеширование паролей (bcrypt)
- JWT-токены для сессий
- Автоматический выход после 24 часов неактивности

**Авторизация:**
- Ролевая модель: пользователь, администратор
- Изоляция данных между пользователями
- Доступ к процессам только для владельца компании

**Защита данных:**
- HTTPS для всех соединений
- Шифрование данных в базе данных
- Регулярное резервное копирование

### 3.3. Требования к масштабируемости

Архитектура системы должна обеспечивать:

- Горизонтальное масштабирование серверов приложений
- Connection pooling для базы данных
- Кэширование статических ресурсов
- CDN для раздачи медиафайлов

### 3.4. Требования к интеграции

**API для внешних систем:**
- REST API для программного доступа
- Документация API в формате OpenAPI 3.0
- Аутентификация через API-ключи

**Экспорт данных:**
- BPMN 2.0 XML для BPMN-платформ
- JSON для программной обработки
- PNG/PDF для документации

## 4. Архитектура системы

### 4.1. Общая архитектура

Система построена по архитектуре клиент-сервер с разделением на три уровня:

```
┌─────────────────────────────────────────────────────────────────┐
│                        Клиентский уровень                        │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │   React     │  │  Tailwind   │  │   Canvas API            │  │
│  │   SPA       │  │  CSS        │  │   (визуализация)        │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                        Серверный уровень                         │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │   Node.js   │  │   tRPC      │  │   LLM Integration       │  │
│  │   Express   │  │   API       │  │   (Claude API)          │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                        Уровень данных                            │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │ PostgreSQL  │  │   S3        │  │   Whisper API           │  │
│  │   (БД)      │  │ (файлы)     │  │   (транскрипция)        │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

- Process → ProcessVersion (1:N)
- Process → ChangeRequest (1:N)
- Process → Recommendation (1:N)

## 5. Пользовательские сценарии

### 5.1. Сценарий: Создание нового бизнес-процесса

**Предусловия:** Пользователь авторизован в системе

**Основной поток:**

1. Пользователь переходит в раздел "Компании"
2. Пользователь выбирает существующую компанию или создаёт новую
3. Пользователь нажимает "Создать процесс"
4. Система предлагает выбрать режим анкетирования (полный/экспресс)
5. Пользователь отвечает на вопросы анкеты (текстом или голосом)
6. Система сохраняет ответы и отображает прогресс
7. После завершения анкеты пользователь нажимает "Сгенерировать процесс"
8. Система отображает индикатор прогресса генерации
9. Система отображает сгенерированный процесс в виде Swimlane-диаграммы
10. Пользователь просматривает процесс и рекомендации

**Альтернативные потоки:**

- 5а. Пользователь прерывает заполнение анкеты → Система сохраняет черновик
- 8а. Ошибка генерации → Система отображает сообщение об ошибке и предлагает повторить

### 5.2. Сценарий: Редактирование бизнес-процесса

**Предусловия:** Существует сгенерированный бизнес-процесс

**Основной поток:**

1. Пользователь открывает страницу процесса
2. Пользователь нажимает "Запросить изменения"
3. Система открывает панель запроса изменений
4. Пользователь описывает желаемые изменения текстом
5. Пользователь нажимает "Создать запрос"
6. Система обрабатывает запрос и генерирует предпросмотр
7. Система отображает diff изменений (добавлено/удалено/изменено)
8. Пользователь просматривает изменения
9. Пользователь нажимает "Применить" для подтверждения
10. Система сохраняет текущую версию и применяет изменения

**Альтернативные потоки:**

- 9а. Пользователь нажимает "Отменить" → Изменения не применяются
- 10а. Пользователь позже нажимает "Откатить" → Система восстанавливает предыдущую версию

### 5.3. Сценарий: Экспорт процесса

**Предусловия:** Существует сгенерированный бизнес-процесс

**Основной поток:**

1. Пользователь открывает страницу процесса
2. Пользователь нажимает кнопку экспорта в панели управления диаграммой
3. Пользователь выбирает формат экспорта (PNG/BPMN XML/PDF)
4. Система генерирует файл в выбранном формате
5. Браузер скачивает файл на устройство пользователя

## 7. Система токенов и тарификация

### 7.1. Модель токенов

Система использует внутреннюю валюту — токены — для оплаты операций с ИИ:

| Операция | Стоимость (токенов) |
|----------|---------------------|
| Генерация бизнес-процесса | 1000 |
| Регенерация процесса | 1000 |
| Запрос изменений | 500 |
| Генерация рекомендаций | 200 |
| Транскрипция аудио (за минуту) | 10 |

### 7.2. Управление балансом

**Отображение баланса:**
- В шапке сайта для авторизованных пользователей
- На странице личного кабинета
- Перед выполнением платных операций

**Проверка баланса:**
- Автоматическая проверка перед операцией
- Блокировка операции при недостаточном балансе
- Информативное сообщение о необходимости пополнения

**Пополнение баланса:**
- Через интерфейс личного кабинета
- Интеграция с платёжными системами (опционально)

## 9. Развёртывание и эксплуатация

### 9.1. Требования к инфраструктуре

**Серверы приложений:**
- Node.js 22.x
- Минимум 2 ГБ RAM
- 2 vCPU

**База данных:**
- PostgreSQL 15.x
- Минимум 10 ГБ хранилища
- SSL-соединение

**Файловое хранилище:**
- Amazon S3 или совместимое
- Публичный доступ для статических файлов

### 9.2. Переменные окружения

| Переменная | Описание |
|------------|----------|
| DATABASE_URL | Строка подключения к PostgreSQL |

| CLAUDE_API_KEY | API-ключ для Claude |
| S3_BUCKET | Имя S3-бакета |
| S3_REGION | Регион S3 |
| S3_ACCESS_KEY | Ключ доступа S3 |
| S3_SECRET_KEY | Секретный ключ S3 |

1. Клонирование репозитория

3. Настройка переменных окружения
4. Применение миграций БД: `pnpm db:push`
5. Сборка проекта: `pnpm build`
6. Запуск сервера: `pnpm start`
